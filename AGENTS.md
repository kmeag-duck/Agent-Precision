# AGENTS.md

Research prototype: an LLM orchestrator that rewrites numerical kernels (Kokkos C++ / CUDA) to lower-precision where safe. Single Python package (`workflow/`), Anthropic SDK, no build system, no CI.

**The author is building this in deliberate baby steps as a learning exercise** in agent orchestration and tool-calling. Resist the urge to add abstractions, frameworks, or features that haven't been explicitly requested. Prefer the smallest concrete change that answers the immediate question. When in doubt, ask before expanding scope.

## Run

```bash
set -a; source .env; set +a            # .env is NOT auto-loaded
pip install -r requirements.txt        # runtime: anthropic; dev: pytest
python -m workflow.run <kernel_file> [--sig-figs N | --decimal-digits N] [--auto] [--no-probe]
# e.g. python -m workflow.run test-kernels/kokkos/mixed/nbody_force.cpp --sig-figs 6
```

`--auto` bypasses the HITL `y/n/q` pause before every tool call (every tool is approved automatically) and writes a JSONL trace of every executed tool to `baselines/<kernel_stem>/orchestrator_trace.jsonl` (`{turn, tool_name, tool_input, exec_result}` per record, truncated at the start of each auto run; synthesized finish-gate errors and the honored `finish` call are both recorded, user rejections cannot occur in this mode). `MAX_TURNS` (150) is the only backstop against runaway loops here — raised from 60 to make room for the per-variable analyst pipeline (see "The per-variable analyst pipeline" below: ~22 extra tool calls on the happy path for a ~10-candidate kernel, plus headroom for verifier-driven finalizer reruns and larger candidate counts). Use this for batch / consistency measurements; not for first-time debugging of a kernel.

`--no-probe` opts out of the probe pipeline. When the input is a Kokkos `.cpp` kernel and `--no-probe` is NOT given, the orchestrator runs an 8-cell precision sweep (4 precisions × 2 RNG seeds) before the per-variable analyst pipeline (`spawn_candidate_finder` and its downstream `spawn_variable_analyst` / `spawn_analyst_finalizer` calls) and feeds the per-output statistics into each of those agents' tasks as a descriptive evidence block (no verdict hints; see `_format_probe_evidence_for_analyst` in `orchestrator.py`, auto-attached by `_execute_tool` — the LLM never passes it through). Non-Kokkos profiles silently skip the probe regardless of this flag — `LanguageProfile.probe_precisions` is empty for CUDA / HIP / SYCL / OMP-offload in v0. Probe failures are non-fatal: missing cells are tolerated by `probe_compare` (only a missing `quad_seed42` ground-truth cell hard-errors) and the analyst pipeline still runs with whatever evidence was produced.

`ANTHROPIC_API_KEY` is read from the environment by the `anthropic` client. There is no other config file for the workflow.

`AGENT_PRECISION_KOKKOS_ROOT` (optional) is read by `workflow/tools.py:compile_baseline_driver` and must point at a Kokkos install prefix (the directory containing `include/` and `lib/`). It is only consulted when the orchestrator calls the `compile_baseline_driver` tool, i.e. only after a successful `spawn_baseline_harness` on a Kokkos `.cpp` input. When unset, the tool returns `status='error'` and the rest of the pipeline continues (the compiled driver is a side artifact). The repo has a local Kokkos install at `./kokkos/` for this purpose; set `AGENT_PRECISION_KOKKOS_ROOT=$PWD/kokkos` before running the workflow directly (`python -m workflow.run ...`) if you want the baseline driver to actually compile. Both Argo wrapper scripts (`scripts/run-argo.sh`, `scripts/run-argoproxy.sh`) auto-default this var to `${PWD}/kokkos` when it is unset and that directory looks like a Kokkos prefix (has `include/` and `lib/`), so the compile tool works out of the box from the repo root via either wrapper; an explicit value in the caller's environment is honored unchanged. The name is deliberately namespaced so it doesn't collide with Kokkos's own CMake convention (`Kokkos_ROOT`) or with a system-wide install.

`AGENT_PRECISION_ANALYST_K` / `AGENT_PRECISION_ANALYST_T` (both optional, defaults `1` / `0.7`) are **inert on the production path**. The per-variable analyst pipeline (`spawn_candidate_finder` → `spawn_variable_analyst` → `spawn_analyst_finalizer`) replaced the monolithic `spawn_analyst`, which is no longer LLM-visible (it is not in `ORCHESTRATOR_TOOLS`). The `spawn_analyst` branch of `_execute_tool` — including its K-fold `run_agent_ensemble` + `aggregate_analyst_verdicts` dispatch — is retained only as a **tests-only backdoor** so the aggregator machinery (`workflow/aggregator.py`) stays covered without a parallel invocation harness; production runs never enter that branch. When empirical per-variable gating (Step 3 `test_variable_downcast` + Step 4 `test_variable_union_downcast` / `bisect_variable_downcast`) supersedes what the ensemble aggregator used to buy us, these env vars can be deleted outright. Do not resurrect them as a "just in case" ensemble knob on the new pipeline — the pipeline's empirical steps are the consistency mechanism.

`AGENT_PRECISION_VERIFIER_K` (optional, default `3` — the full panel) is read by `workflow/orchestrator.py:_execute_tool` on the `spawn_verifier` branch. When `> 1`, it must be `<= len(VERIFIER_LENSES)` (currently 3 — faithfulness, budget, edge_cases) — exceeding the lens count is a configuration error, not a replication multiplier (a `ValueError` is raised). The orchestrator runs the verifier K times in parallel via `verifier_panel.run_verifier_panel` at temperature `AGENT_PRECISION_VERIFIER_T` (default `0.7`), with each call using `run_agent(..., system_prompt_suffix=lens['suffix'])` so the base prompt in `registry.py` stays the single source of truth. The K verdicts are folded through `aggregate_verifier_verdicts`: strict-accept (any single lens reject flips the whole verdict to reject), `per_variable` from the faithfulness lens (lens 0) verbatim, `concerns` unioned across lenses, deduped by exact string after `.strip()`, and prefixed with `[<lens_name>]`. The aggregated dict conforms to `VERIFIER_OUTPUT_SCHEMA`, so `_FinishGateState` and the rewriter-retry prompt construction need no changes. The disagreement report is returned alongside the result as `verifier_aggregator_metadata`. Setting `K=1` opts out of the panel entirely and takes the single-shot path (three verifier LLM calls per accepted verdict → one). The default was raised from `1` to `3` when the registry moved to `claude-sonnet-4-6` (which accepts `temperature`, so lens diversity is real rather than collapsed to internal sampling).

`AGENT_PRECISION_RUN_TIMEOUT_SEC` (optional) is read by `workflow/tools.py:run_baseline_driver` and must be a positive integer (seconds). It bounds wall-clock time for the compiled baseline driver subprocess. Defaults to `60` when unset; an invalid value (non-int, ≤0) makes the tool return `status='error'` without invoking the subprocess. The `_SEC` suffix is deliberate to avoid ms/s ambiguity; the name is namespaced for the same reason as `AGENT_PRECISION_KOKKOS_ROOT`. Both Argo wrapper scripts auto-default it to `60`; an explicit value in the caller's environment is honored unchanged. Like the compile tool, a timeout or non-zero exit is non-fatal — the rest of the pipeline continues.

`--sig-figs` and `--decimal-digits` are mutually exclusive and exactly one is REQUIRED (argparse rejects a run with neither at exit code 2; the operator sees `usage:` + `one of the arguments --sig-figs/--decimal-digits is required`). The prior contract also accepted no flag and asked a `precision_advisor` LLM to infer one, with a `sig_figs=6` fallback when the advisor returned `unknown`; that agent was removed to eliminate a whole class of "silent tolerance drift" surprises where a batch run's numerical target depended on an opaque per-kernel inference. The tolerance dict threaded through `run_orchestrator` is now always `{kind, value, source:'user_cli'}`; `run_orchestrator` requires the `tolerance` kwarg (no default). Both Argo wrapper scripts (`run-argo.sh`, `run-argoproxy.sh`) forward `"$@"` so flags pass through unchanged.

**Test-config side-channel** (`<kernel>.testconfig.json`). If a file named `<kernel_file>.testconfig.json` sits next to the kernel source, `workflow/run.py:_load_test_config` auto-loads it and threads the parsed dict through `run_orchestrator(..., test_config=...)` into the initial user message as a `TEST CONFIG (JSON):` block inside the `BASELINE STEP` portion. The Kokkos baseline_harness system prompt tells the agent to use those values verbatim (N, RNG seed, scalar parameters, per-array distribution / low / high / etc.) instead of inventing them. The schema is freeform JSON — the harness prompt describes the conventional keys per kernel — but the top-level value MUST be a JSON object; a list, scalar, or malformed JSON is a hard CLI error (`SystemExit`) rather than a silent fallback (the operator explicitly opted in by dropping the file, so a quiet fallback to "harness invents inputs" would defeat the point). No CLI flag governs this; the presence of the sibling file IS the opt-in. The motivating case is the N=5 nbody_force consistency sweep where five runs picked wildly different N / eps / dt combinations across attempts, making probe evidence and comparator results non-comparable across runs. `test-kernels/kokkos/mixed/nbody_force.cpp.testconfig.json` is the v0 fixture (N=1024, seed=42, eps=0.05, dt=0.01, uniform position/velocity/mass ranges). Only the Kokkos harness prompt currently documents key semantics; the four other v0 profiles will still receive the block if a config file is present but the harness has no contract for consuming it — do not drop `.testconfig.json` files next to non-Kokkos kernels in v0.

### Running via Argo (Argonne) instead of api.anthropic.com

```bash
./scripts/run-argo.sh test-kernels/kokkos/mixed/nbody_force.cpp
```

`run-argo.sh` brings up an SSH tunnel (`:8082` → `apps.inside.anl.gov:443` via `homes.cels.anl.gov`) and a local Anthropic-compatible shim (`claude-argo-proxy.py` on `:8083`), then runs `python -m workflow.run` with:

- `ANTHROPIC_BASE_URL=http://127.0.0.1:8083/argoapi/`
- `ANTHROPIC_AUTH_TOKEN=$USER` (Argonne username, not an API key)

The `anthropic` SDK honors both env vars, so no workflow code changes are required to switch backends. If the tunnel and/or proxy are already running (e.g. started by another tool in the same session), the script reuses them and does not kill them on exit.

The shim script is expected at `~/argo-shim-lite/claude-argo-proxy.py` (override with `ARGO_PROXY_SCRIPT=...`); it depends on `aiohttp`. The reference implementation this was modeled on lives at `~/Agentic-Mixed-Precision-Demo/run-argo.sh`.

### Or: use the local argo-proxy on :52675 (no SSH tunnel, no Duo)

```bash
./scripts/run-argoproxy.sh test-kernels/kokkos/mixed/nbody_force.cpp
```

`argo-proxy serve` (the same daemon OpenCode's `provider.argo` depends on) natively exposes an Anthropic-compatible `/v1/messages` route at `http://127.0.0.1:52675/v1/`. The wrapper just `curl`s `/health`, then runs `python -m workflow.run` with `ANTHROPIC_BASE_URL=http://127.0.0.1:52675/` and `ANTHROPIC_AUTH_TOKEN=$USER` (any non-empty string; argo-proxy ignores it). The base URL is the bare host root, not `…/v1/`: the anthropic SDK (≥0.x) appends `v1/messages` itself, so a `/v1/` in `ANTHROPIC_BASE_URL` produces a `/v1/v1/messages` request and a 404 from argo-proxy. The `provider.argo` entry in `opencode.json` uses `"baseURL": "http://localhost:52675/v1"` — that's a different SDK convention (OpenAI-route compatibility) and is unaffected by this rule.

Prereq: `argo-proxy serve` is already running. argo-proxy has persistent auth set up at pipx-install time, so there's no per-session Duo prompt.

Use `scripts/run-argo.sh` instead only when `argo-proxy` isn't installed on this host — that script's SSH tunnel + `claude-argo-proxy.py` shim is a self-contained fallback. Both paths terminate at the same upstream Argo service, but they are **not** interchangeable for model ids: `argo-proxy` normalizes model names before forwarding, while `claude-argo-proxy.py` is a transparent forwarder. The id Argo's `/v1/messages` upstream actually accepts is `claude-opus-4-7` (hyphen, no prefix); see "Model names look wrong but aren't" below.

## Architecture (don't redesign this)

- `workflow/registry.py` — `AGENTS` dict is the single source of truth for agent types. Each entry = `{system_prompt, output_schema, model, supports_temperature}`. **Adding a new agent type = one new entry here, nothing else changes.** `supports_temperature` is a mandatory bool (no implicit default) that gates whether `run_agent` forwards the `temperature` kwarg to `messages.create`. All current entries use `claude-sonnet-4-6` with `supports_temperature=True` — sonnet-4-6 accepts `temperature`, so ensemble diversity (verifier K, and the tests-only analyst K) is real rather than collapsed to whatever internal stochasticity the model provides. Some Argo snapshots (notably `claude-opus-4-7`, which was the prior default for every entry) reject `temperature` with HTTP 400 (`"temperature is deprecated for this model"`); the drop-and-warn mechanism is retained for exactly that case — flip a per-entry `supports_temperature` to `False` before switching that entry to such a model. When `False`, an explicit `temperature` request is dropped silently on the wire and the operator gets a single one-shot stderr warning per (process, agent type) — `run_agent` exposes the warned-set as `_TEMPERATURE_DROP_WARNED` for testability. The ensemble path still runs the requested number of calls when `supports_temperature=False`, but its diversity collapses accordingly; the warning makes that consistency hazard visible in the JSONL trace's `aggregator_metadata`.
- `workflow/run_agent.py` — generic `run_agent(type, task, temperature=None, system_prompt_suffix=None) -> dict`. Forces the agent to call a `submit_result` tool whose schema is the registry's `output_schema`. Never edit this when adding agent types. When `temperature` is `None`, `DEFAULT_SINGLE_SHOT_TEMPERATURE` (currently `0.0`) is passed to the SDK — the prior contract was "omit and let the API default apply", which read as deterministic but actually produced high-variance output (~1.0 default); the new contract makes single-shot reproducibility the default and forces callers who want diversity (the ensemble path) to pass an explicit value. Pass an explicit float to override; ensemble callers pass `AGENT_PRECISION_ANALYST_T` / `AGENT_PRECISION_VERIFIER_T` (default `0.7`). Also includes two defensive guards on the SDK response: (1) if `response.content` is `None` (seen on some Argo proxy configurations that accept malformed message bodies), `run_agent` raises a `RuntimeError` naming the `stop_reason` and `response.id` instead of letting a downstream `TypeError` surface; and (2) if the `submit_result` `tool_use.input` is a `str` instead of a `dict` (observed on the `:8083` `claude-argo-proxy.py` transparent shim path — some upstream Argo responses ship `input` as a JSON-encoded string that never got re-decoded), `_coerce_tool_input_to_dict` silently `json.loads` it and returns the resulting dict; if it can't be decoded, or decodes to a non-object (list, scalar), or `tool_use.input` is neither `dict` nor `str`, it raises a `RuntimeError` naming the agent + response id (same idiom as the `content=None` guard). This turns what was previously an `'str' object has no attribute 'get'` mystery-traceback six frames deep in `aggregate_analyst_verdicts` (concrete failure mode: K=3 nbody_force retry run, 2026-07-01) into either a transparent proxy-quirk workaround or a diagnosable error at the source. `system_prompt_suffix` appends a per-call addendum after the registry's base prompt (used by the verifier panel's lens system, so the base prompt remains the single source of truth). `max_tokens` is set to `32768` (raised from `8192` because the Kokkos v1 baseline_harness emits four full per-precision drivers in one `submit_result` call — see `workflow/languages/kokkos.py:BASELINE_HARNESS_OUTPUT_SCHEMA` — and four drivers easily blow past the old ceiling; when the model truncates mid-tool-use it returns `stop_reason='max_tokens'` with a partial/empty `tool_use.input`, surfacing downstream as a baffling "submit_result payload has no keys" `RuntimeError` in `orchestrator._execute_tool`). To accompany that bump, an explicit `timeout=600.0` is passed on every `messages.create` call: the SDK refuses non-streaming requests whose own conservative duration estimate (a function of `max_tokens`) exceeds 10 minutes, raising `ValueError("Streaming is required for operations that may take longer than 10 minutes.")` at create time; an explicit `timeout` is the SDK-sanctioned escape hatch that signals "operator accepts responsibility for this duration" and skips that guard. As a runtime tripwire, `run_agent` also warns to stderr (once per call) when `response.stop_reason != "tool_use"` — `tool_choice` forces `submit_result`, so any other stop reason (typically `max_tokens` from a regrown schema, or `end_turn` from a proxy stripping `tool_choice`) is a smoking gun for the truncated-payload failure mode and makes the WHY visible without rerunning. Also exports `run_agent_ensemble(type, task, k, temperature) -> list[dict]` — a `ThreadPoolExecutor` fan-out that returns the K result dicts in submission order. `k=1` skips the thread pool so the single-shot path stays trivially testable; failures propagate (one exception fails the whole ensemble, caller decides retry vs. fallback).
- `workflow/aggregator.py` — `aggregate_analyst_verdicts(verdicts) -> (aggregated, report)`. Per-variable plurality vote with `keep > emulate > downcast` conservative tiebreak (rationale: false-conservative is recoverable via one more trip through the dynamic-verification chain; false-aggressive is a silent precision regression). Variable names are normalized lowercase+strip before voting; omitted variables count as 'keep' votes; `target_precision` / `emulation_type` / `reason` are taken from the verdicts that voted for the WINNING action (so a downcast winner doesn't inherit a target_precision from a 'keep' voter). Rework is a **strict** majority vote on `suggested` (ties default to False — kernel-shape changes are aggressive); if false, all rework fields are zeroed regardless of minority content. `precision_budget` and `overall_notes` are echoed from the "most-aligned" verdict (the one whose per-variable answers match the consensus on the most variables; ties broken by input order) — so the budget block stays internally consistent with the chosen verdict instead of stitching prose from incompatible sources. The disagreement report (`{k, variable_disagreements, rework_disagreement?, consensus_source_verdict_index}`) is for the orchestrator trace, not for downstream agents.
- `workflow/verifier_panel.py` — `VERIFIER_LENSES` (ordered: `faithfulness`, `budget`, `edge_cases`; lens 0 is the convention-source for `per_variable`), `run_verifier_panel(task, lenses, temperature) -> list[dict]` (parallel `ThreadPoolExecutor` over `run_agent('verifier', task, ..., system_prompt_suffix=lens['suffix'])`), and `aggregate_verifier_verdicts(verdicts, lens_names) -> (aggregated, report)`. Aggregation: STRICT verdict (accept iff every lens accepted — same conservative bias as the analyst aggregator), `per_variable` from the faithfulness lens verbatim (the budget and edge_cases lenses fill it in to satisfy the schema but their entries are intentionally dropped; this is **not** a vote — lenses are specialized, not redundant), `concerns` unioned across lenses, deduped by exact-string after `.strip()`, prefixed `[<lens_name>] ` in first-seen order (so a rewriter-retry prompt sees which lens raised which concern — the primary win of the panel). Disagreement report: `{k, lens_verdicts, dissenting_lenses, concerns_by_lens}`. If you add or remove a lens, the K cap and the suffix prompts change together — update `VERIFIER_LENSES` and the asserting tests in `tests/test_verifier_panel.py` in the same change.
- `workflow/orchestrator.py` — itself a Claude conversation. LLM-visible tools are one-per-agent-type: `spawn_candidate_finder`, `spawn_variable_analyst`, `spawn_analyst_finalizer` (the per-variable analyst pipeline that replaced the monolithic `spawn_analyst` — see "The per-variable analyst pipeline" below), `spawn_rewriter`, `spawn_verifier`, and `spawn_baseline_harness`. Plus ten deterministic (non-LLM) tools defined in `workflow/tools.py`: `compile_baseline_driver`, `run_baseline_driver`, `probe_step`, `probe_compare`, `test_variable_downcast`, `test_variable_union_downcast`, `bisect_variable_downcast`, `splice_rewritten_kernel`, `compile_rewritten_driver`, `run_rewritten_driver`, `compare_outputs`, and `measure_speedup`. Plus `finish`. Contains the **human-in-the-loop pause** (`_hitl_pause`): every tool call is shown and the user must approve `y/n/q` before it runs. This pause is the whole point of v0 in interactive mode — do not remove it. The `--auto` CLI flag (threaded to `run_orchestrator(..., auto=True)`) skips the pause for batch runs and instead journals every executed tool to `baselines/<kernel_stem>/orchestrator_trace.jsonl` via `_append_trace`; auto-mode is the ONLY supported way to bypass the pause. A `MAX_TURNS=150` backstop guards against runaway loops if the HITL is left unattended or if `--auto` is left unattended (raised from 60 to make room for the per-variable analyst pipeline — ~22 extra tool calls on the happy path for a ~10-candidate kernel, plus headroom for verifier-driven finalizer reruns and larger candidate counts); don't raise it casually. The `spawn_verifier` branch of `_execute_tool` consults `AGENT_PRECISION_VERIFIER_K` (default `3` — the full panel; set to `1` to opt back into single-shot) to decide between single-shot and panel dispatch; see the env-var section above for the contract. `verifier_aggregator_metadata` is returned alongside the result for the trace; the orchestrator LLM sees it as part of the tool result. The `spawn_analyst` branch is retained as a tests-only backdoor (see `AGENT_PRECISION_ANALYST_K` above) and is NOT in `ORCHESTRATOR_TOOLS`.
- `workflow/run.py` — thin CLI; takes a kernel path plus optional `--sig-figs N` / `--decimal-digits N` and `--auto`, normalizes the tolerance flag into `{kind, value, source:'user_cli'}` (or `None`), passes that as the `tolerance` kwarg and `--auto` as the `auto` kwarg to `run_orchestrator`, then prints final code + notes.

Rejecting (`n`) returns `{"status": "rejected_by_user"}` to the orchestrator so it can self-correct without burning an agent API call — that behavior is intentional.

The orchestrator system prompt enforces the pipeline `candidate_finder -> per-variable-analyst (fan-out over candidates, interleaved with `test_variable_downcast`) -> `test_variable_union_downcast` (with `bisect_variable_downcast` on union failure) -> analyst_finalizer -> rewriter -> verifier -> finish`, and explicitly forbids calling `finish` unless the most recent `spawn_verifier` returned `verdict='accept'`. The tolerance is now always operator-supplied via `--sig-figs` / `--decimal-digits`; the removed `precision_advisor` agent used to sit ahead of the analyst when neither flag was given. `spawn_baseline_harness` is orthogonal to this pipeline (see next section), called at most once per run and only for Kokkos `.cpp` inputs. `compile_baseline_driver`, `run_baseline_driver`, `splice_rewritten_kernel`, `compile_rewritten_driver`, `run_rewritten_driver`, `compare_outputs`, and `measure_speedup` form an eight-step chain off `spawn_baseline_harness`: each is the deterministic follow-up to the previous step, each is called at most once per accepted verifier verdict with the same `kernel_stem`, and a failure or skip at any link prevents (but does not require) the next. `measure_speedup` is the sole exception to "failure prevents finish": it is **non-gating** — any error path (missing `timing` block, malformed values, zero rewritten mean) is reported to the LLM but does not block `finish`. `splice_rewritten_kernel` additionally requires the most recent `spawn_verifier` to have returned `verdict='accept'` — it takes the rewriter's output and splices it between the sentinel lines in `baselines/<stem>/driver.cpp` to produce `baselines/<stem>/rewritten/driver.cpp`. Most of these rules live in the prompt and are trusted to the orchestrator LLM. The **finish-gate** is the exception: it is enforced in code by `_FinishGateState` in `orchestrator.py`, which (a) blocks `finish` until the most recent `spawn_verifier` returned `verdict='accept'` AND, on Kokkos `.cpp` inputs, the most recent `compare_outputs` returned `status='ok'` for the current rewrite cycle, and (b) injects an `{status:'error', is_error:true}` synthetic tool_result naming what's missing if `finish` is called prematurely. `spawn_rewriter` invalidates both tracked statuses (it starts a new rewrite cycle); any splice/compile_rewritten/run_rewritten call invalidates `compare_status` because it overwrites a file the comparator reads. If you change finish-gating, change it in `_FinishGateState` first (source of truth) and keep the system prompt in sync.

### Baseline harness and dynamic verification chain

`baseline_harness` is the first component of the dynamic-verification chain that ends in `compare_outputs` and the code-side finish-gate (see "Architecture" above). It is a one-shot LLM agent that, given a Kokkos C++ kernel, writes a self-contained C++ driver source. When the operator later compiles and runs that driver, it exercises the kernel on fixed inputs (deterministic: `Kokkos::Serial`, fixed RNG seed 42 by default) and writes a reproducible reference output to `./reference.json` using `%.17g` formatting. The five downstream deterministic tools (`compile_baseline_driver`, `run_baseline_driver`, `splice_rewritten_kernel`, `compile_rewritten_driver`, `run_rewritten_driver`) produce the rewritten reference; `compare_outputs` diffs the two under the agreed tolerance; and `measure_speedup` reads the harness-emitted `timing` block from both sides to report a wall-clock speedup, non-gating.

v0 scope is intentionally narrow:

- Per-language profiles. The orchestrator's initial user message contains a `BASELINE STEP` block whose contents are driven by the resolved `LanguageProfile` (see `_format_baseline_block` in `orchestrator.py`): it invites the harness call when `profile.dynamic_verification` is `True` and the suffix matches one of the profile's `source_suffixes`, otherwise it explicitly forbids the call. v0 ships five profiles: **Kokkos** (`.cpp`, smoke-validated end-to-end), **CUDA** (`.cu`, smoke-validated on `vector_add.cu` to comparator step), **HIP** (`.hip`, **unit-tested but not smoke-validated** — no ROCm host available at implementation time; the `hipcc` command shape, default `--offload-arch=gfx90a`, `AGENT_PRECISION_HIP_ARCH` override, preflight error path, and harness prompt are all asserted by `tests/test_tools.py` / `tests/test_registry.py` / `tests/test_languages.py`, but no `.hip` kernel has actually been run through the chain), **SYCL** (`.cpp`, **unit-tested but not smoke-validated** — no SYCL toolchain on the development host at implementation time; the default `icpx -fsycl -std=c++17 -O2` command shape, `AGENT_PRECISION_SYCL_CXX` override, preflight error path, in-order-queue / buffer-accessor mandates in the harness prompt, and cross-profile prompt token isolation are all asserted by the same three test modules, but no `.cpp` SYCL kernel has actually been run through the chain), and **OpenMP-offload** (`.cpp`, **unit-tested but not smoke-validated** — no host with an OMP-offload toolchain (clang++ with offload runtime, `icpx`, or `nvc++`) available at implementation time; the default `clang++ -fopenmp -fopenmp-targets=nvptx64-nvidia-cuda -std=c++17 -O2` command shape, `AGENT_PRECISION_OMP_CXX` override, `AGENT_PRECISION_OMP_TARGET` override, preflight error path, single-team/single-thread launch (`omp_set_num_threads(1)` + `num_teams(1) thread_limit(1)`), `map(to:/from:/tofrom:)` requirement, no-reduction rule in the harness prompt, and cross-profile prompt token isolation are all asserted by the same three test modules, but no `.cpp` OMP-offload kernel has actually been run through the chain). The `.cpp` suffix is now shared between Kokkos, SYCL, and OpenMP-offload; `detect_language()` distinguishes them at runtime by source content (see `_detect_from_source` in `kokkos.py`, `sycl.py`, and `omp_offload.py`), and a `.cpp` source matching none of the three probes — or matching ambiguously — falls back through insertion-order tie-break in `PROFILES` (Kokkos first, then SYCL, then OpenMP-offload). The `.hip` suffix is owned exclusively by the HIP profile in v0; the alternate "HIP-in-`.cpp`" convention (`#include <hip/hip_runtime.h>` in a `.cpp` source) is deferred until the 3-way `.cpp` content-probe collision (Kokkos vs SYCL vs OMP-offload) has shipped, since it would require teaching the probe to disambiguate four candidates instead of three.
- Driver source only. The agent never compiles, runs, or invents numerical output values. Its `submit_result` payload is `{driver_source, kernel_function_name, inputs_summary, output_arrays}` (see `BASELINE_HARNESS_OUTPUT_SCHEMA` in `registry.py`).
- One driver per kernel stem. On HITL approval, `_execute_tool` writes the driver to `baselines/<kernel_stem>/driver.cpp` (relative to the orchestrator's CWD; this is currently the only `_execute_tool` branch that touches the filesystem). `kernel_stem` is derived from `Path(kernel_path).stem` by `run_orchestrator` and passed to the tool via the user message; the orchestrator forwards it back as the `kernel_stem` tool argument. Re-running overwrites the previous driver.
- Syntax-check gate. Before `_execute_tool` writes any harness output to disk, it runs each candidate driver source through `workflow/tools.py:syntax_check_driver_source(profile, source, label)`, which dispatches to the profile's `LanguageProfile.build_syntax_check_command(src_path) -> list[str] | None` hook. Kokkos implements this as `g++ -std=c++20 -fsyntax-only -fopenmp -I<KOKKOS_ROOT>/include <src>` (no `-L`, no `-l<lib>`, no `-o` — parse-only, no code generation); the four other v0 profiles inherit the base-class default, which returns `None` (opt-in per profile). The gate silently skips (returns `None` from `syntax_check_driver_source`) when the profile has no check command, when the profile's command builder returns `None` (Kokkos: `AGENT_PRECISION_KOKKOS_ROOT` unset or its include dir missing), or when `subprocess.run` raises `FileNotFoundError` (compiler not on PATH). On a non-zero compiler exit the gate returns a `{status:'error', ...}` dict with the label (e.g. `drivers['double']` for the v1 multi-driver payload, `driver_source` for v0) and the exact command line folded into stderr alongside the compiler's own diagnostic; `_execute_tool` propagates that dict with `is_error: True` added, and the orchestrator's tool_result construction lifts that key to the SDK-level `is_error` flag so the model retries the harness with the diagnostic verbatim. Write-side is strictly all-or-nothing: `driver_dir.mkdir(...)` is deferred to AFTER the gate passes for every driver in the payload, so a v1 fan-out that fails on the third driver leaves zero files behind (avoids partial writes that later `probe_step` calls would silently reuse). Motivating case is a real `nbody_force` run whose harness emitted `vxType vx(...); vyType_v vy(...);` — two inconsistent alias-naming conventions in one line — that the write-first path let through only for `compile_baseline_driver` to reject downstream, burning a full HITL cycle. The gate is a quality improvement, not a hard prerequisite: hosts without a compiler still run the pipeline normally, they just don't get pre-write validation. If you add a new profile and want the gate active, implement `build_syntax_check_command` returning a parse-only command (no linker, no code-gen); the four dispatch tests in `tests/test_orchestrator.py` (gate-passes-v0, gate-rejects-v0, gate-passes-v1, gate-rejects-v1) plus the five unit tests in `tests/test_tools.py` (skip-on-none, pass-on-zero-exit, error-dict-on-nonzero, skip-on-FileNotFoundError, tempfile-suffix/cleanup) pin the contract.
- Splice sentinels. The harness prompt mandates that the inlined kernel be bracketed by the exact lines `// ---- KERNEL BEGIN ----` and `// ---- KERNEL END ----` (each on its own line, no indentation, no paraphrasing). These are a hard contract for a later mechanical-verification step that string-replaces the text between them to swap in a rewritten kernel against bit-identical inputs / RNG / JSON output. If you change the sentinel strings, update `BASELINE_HARNESS_SYSTEM_PROMPT` in `registry.py`, the `KERNEL_BEGIN_SENTINEL` / `KERNEL_END_SENTINEL` constants and the `splice_rewritten_kernel` body in `workflow/tools.py`, and the asserting test in `tests/test_registry.py` together.
- Precision-alias contract (Option 4 splice-scope fix). `splice_rewritten_kernel` only replaces text between the kernel sentinels, but a precision downcast on a kernel parameter changes the parameter type, which the caller in `main()` — outside the sentinels — also sees. To make those rewrites compile, the baseline harness emits a `using <ParamName>Type = ...;` alias per floating-point kernel parameter immediately inside the kernel sentinels, the kernel function header uses those aliases, and `main()` outside the sentinels constructs kernel arguments through the same aliases. The rewriter, when downcasting a parameter the analyst named, redefines only the corresponding alias and leaves the function header untouched; this propagates through `main()` for free. Aliases are emitted for every floating-point parameter (scalars and Views); integer parameters (sizes, counts, indices) are excluded. Naming is per-variable (one `<ParamName>Type` alias per kernel parameter), not per-type, because analyst verdicts are per-variable. For kernels without the alias pattern (legacy harness output), the rewriter falls back to editing the function header directly. Staging-view sub-rule for `View<const T*>` parameters: the writable staging view that populates a const-aliased kernel argument must derive its element type from the alias (`Kokkos::View<typename aType::non_const_value_type*>`), not hardcode it to `double` — discovered on `nbody_force` where the harness emitted `Kokkos::View<double*> m_nc` and the alias-only rewrite broke at the `mType m = m_nc;` conversion line. The contract lives entirely in `BASELINE_HARNESS_SYSTEM_PROMPT` and `REWRITER_SYSTEM_PROMPT`; `splice_rewritten_kernel` itself is unchanged. If you change the alias naming convention, update both prompts and the asserting tests in `tests/test_registry.py` together. Known v0 limitation: kernels that downcast an *output* View aren't fully covered — `main()`'s JSON dump-code uses `Kokkos::View<double*>` directly for output extraction. None of the current `test-kernels/` cases hit this; revisit when one does.
- The baseline reference is **not** fed into the analyst, rewriter, or verifier in this run; they reason from source. The reference becomes load-bearing only at the comparator step at the end of the chain (see `compare_outputs` below), which on `.cpp` inputs gates `finish`.

`run_orchestrator(..., kernel_name: str | None = None)` accepts an optional explicit kernel function name to disambiguate which function the harness should target; when given, a `TARGET KERNEL: <name>` line is added to the `BASELINE STEP` block. The CLI does not expose this flag in v0 (the agent infers the function from a single-kernel source). When multi-kernel inputs eventually land, the per-stem directory will likely evolve to `baselines/<file_stem>__<kernel_name>/`.

Compilation of the driver is handled by a separate deterministic (non-LLM) orchestrator tool, `compile_baseline_driver`, defined in `workflow/tools.py`. The orchestrator prompt instructs the LLM to call it exactly once, immediately after a successful `spawn_baseline_harness`, passing the same `kernel_stem`. The tool reads `AGENT_PRECISION_KOKKOS_ROOT` (see the env-var note at the top of this file), shells out to `g++ -std=c++20 -O2 -fopenmp -I$ROOT/include -L$ROOT/lib baselines/<stem>/driver.cpp -lkokkoscore -lkokkoscontainers -lpthread -ldl -o baselines/<stem>/driver`, and returns `{status, stdout, stderr, artifacts}`. That shape is the same one the planned dynamic-verification tools will return (see "Planned next steps") so the orchestrator's tool-result handling doesn't change when "compile locally" becomes "submit compile job and poll". The repo's bundled Kokkos at `./kokkos/` was built as static archives with the OpenMP host backend, which is why the flag set is fixed — there is no rpath because the binary has no `libkokkos*` in its dynamic NEEDED list. Like the baseline itself, a failed compile is non-fatal: the analyst -> rewriter -> verifier pipeline still runs and `finish` is still reachable.

Execution of the compiled driver is a third deterministic (non-LLM) orchestrator tool, `run_baseline_driver`, also defined in `workflow/tools.py`. The orchestrator prompt instructs the LLM to call it exactly once, immediately after a successful `compile_baseline_driver`, passing the same `kernel_stem`. The tool checks that `baselines/<stem>/driver` exists and is executable, deletes any stale `baselines/<stem>/reference.json` from a prior run (so a failed run cannot leave a misleadingly-stale file in place), then `subprocess.run(["./driver"], cwd="baselines/<stem>", capture_output=True, text=True, check=False, timeout=AGENT_PRECISION_RUN_TIMEOUT_SEC)`. On a clean exit it requires the driver to have written `reference.json` and validates that it parses as JSON; the shape of that JSON (`{kernel, seed, inputs, outputs}` per the harness contract) is checked at the comparator step. The tool returns the same `{status, stdout, stderr, artifacts}` dict as `compile_baseline_driver`, with `artifacts=["baselines/<stem>/reference.json"]` on success and `[]` on any error path. The body of this function (env-var parsing, preflight checks, stale-reference deletion, subprocess invocation, timeout handling, JSON validation) is shared with `run_rewritten_driver` via a private `_run_driver(driver_dir, missing_binary_hint)` helper; the two wrappers differ only in cwd and in which upstream tool the missing-binary error hint blames. Like the compile step, a baseline-run error is non-fatal to the LLM pipeline, but it transitively blocks `finish` on `.cpp` inputs because the comparator cannot read a reference that does not exist.

After a `spawn_verifier` returns `verdict='accept'`, the orchestrator enters the **rewritten chain** — four more deterministic (non-LLM) tools, all in `workflow/tools.py`, all returning the same `{status, stdout, stderr, artifacts}` shape, all writing under `baselines/<stem>/rewritten/` without ever touching the baseline tree.

`splice_rewritten_kernel(kernel_stem, rewritten_kernel_source)` is pure text I/O. It reads `baselines/<stem>/driver.cpp`, finds the unique `// ---- KERNEL BEGIN ----` and `// ---- KERNEL END ----` sentinel lines (byte-exact, each on its own line with no surrounding indentation — same contract the harness prompt mandates), replaces the text strictly between them with `rewritten_kernel_source`, and writes the result to `baselines/<stem>/rewritten/driver.cpp`. Sentinel constants live in `workflow/tools.py` (`KERNEL_BEGIN_SENTINEL`, `KERNEL_END_SENTINEL`); the splice contract relies on the precision-alias pattern emitted by the harness so a precision downcast on a kernel parameter propagates through `main()` outside the sentinels without requiring a signature-touching rewrite (see the alias bullet above).

`compile_rewritten_driver(kernel_stem)` and `run_rewritten_driver(kernel_stem)` are the rewritten-tree analogues of `compile_baseline_driver` and `run_baseline_driver`. Each shares its baseline counterpart's env-var contract (`AGENT_PRECISION_KOKKOS_ROOT` for compile, `AGENT_PRECISION_RUN_TIMEOUT_SEC` for run) and core implementation via the `_compile_driver` / `_run_driver` helpers; only the target directory and missing-source/missing-binary hint differ. They produce `baselines/<stem>/rewritten/{driver, reference.json}` from the spliced source. The two pairs of wrappers were structured this way so future remote-batch versions ("submit compile/run job and poll") can drop in by replacing the helper bodies without rewiring four call sites.

`measure_speedup(kernel_stem)` is the final and only **non-gating** tool of the chain. It runs exactly once per accepted verifier verdict, immediately after `compare_outputs` returns `status='ok'`; the orchestrator LLM is told to call it, and the finish-gate treats both its ok and error paths as pure no-ops (`_FinishGateState.observe` does not track it). The tool reads the `timing` block that the baseline harness contract requires every driver to emit into its `reference.json` (top-level key `timing = {trials_timed, mean_sec, stddev_sec, min_sec, max_sec}`, hardcoded N=11 trials = 1 warmup + 10 timed, `%.9g` formatting, population stddev), extracts both the baseline and rewritten timings, computes `speedup = baseline_mean / rewritten_mean` with ratio error propagation (`speedup_stddev = speedup * sqrt((σ_b/μ_b)² + (σ_r/μ_r)²)`), and writes `baselines/<stem>/rewritten/timing.json` (`{baseline, rewritten, speedup, speedup_stddev, trials_timed}`) on the ok path only. On any error path (missing `timing` key on either side, wrong field types, `trials_timed` mismatch, zero rewritten mean triggering a divide-by-zero) the tool returns `{status:'error', ...}` with a diagnostic and writes nothing — the LLM sees the error, `_FinishGateState` ignores it, and `finish` proceeds. Kokkos is the only smoke-validated profile; the other four v0 profiles (CUDA / HIP / SYCL / OMP-offload) also emit a `timing` block per their harness prompts but the end-to-end `measure_speedup` path is unit-tested only. Source of truth is `workflow/tools.py` (`measure_speedup`, `_extract_timing`, `_TIMING_REQUIRED_KEYS`); the harness-side `timing` block contract lives in each `workflow/languages/<id>.py` baseline-harness prompt, and the parametrized `test_baseline_harness_prompt_documents_timing_block` in `tests/test_languages.py` pins that all five profiles document it consistently.

`compare_outputs(kernel_stem, tolerance_json)` is the load-bearing tool of the chain — it is what turns the splice → compile → run cascade from a stack of side artifacts into a real `finish` precondition. It parses the supplied tolerance (`{kind, value, source}`, with `kind` either `sig_figs` or `decimal_digits`), loads both `reference.json` files, performs a shape check (same top-level keys; same `outputs` array names; same per-array lengths; equal `kernel` and `seed`), and walks every pair under `outputs/` applying the per-kind threshold. Three semantic rules differ from naive IEEE 754: NaN ALWAYS mismatches (even NaN-vs-NaN) so any NaN flags a regression rather than being silently equal; matching same-sign infinities pass, while mismatched inf signs and inf-vs-finite fail; and `sig_figs` treats the both-exactly-zero pair as a pass (the relative-tolerance formula would otherwise reject it). The mismatch list shown in stderr (and stored in `comparison.json`) truncates to the first 10 entries with a `+ K more mismatches suppressed` footer. `baselines/<stem>/rewritten/comparison.json` is written on both pass and fail paths, so an operator always has a machine-readable record of the most recent comparator decision. The orchestrator's `_FinishGateState` reads `status` from this tool's result to decide whether `finish` is allowed on `.cpp` inputs; on a comparator error, the system prompt and the synthetic gate-violation message both steer the LLM back to the per-variable analyst pipeline (not `spawn_rewriter`) for the retry, because a numerical mismatch usually indicates the verifier's verdict was wrong rather than just the implementation.

### Probe pipeline

The probe pipeline is a pre-analyst empirical sweep that runs the kernel under several internal precisions and surfaces per-output statistics into the analyst's task as descriptive evidence — no verdicts, no hints, no rubber-stamping. Goal: replace the analyst's a-priori reasoning about "is float enough?" with concrete numbers it can fold into its per-variable decisions. The probe is gated by two things: `LanguageProfile.probe_precisions` (empty disables the probe — silent skip, same idiom as `dynamic_verification`) and the `--no-probe` CLI flag (operator opt-out). In v0 only the Kokkos profile defines a non-empty `probe_precisions = ("quad", "double", "float", "mixed_io")` and a `baseline_precision = "quad"`; CUDA / HIP / SYCL / OMP-offload all set `probe_precisions = ()`. The probe is NOT finish-gating — `_FinishGateState.observe` does not track probe tools.

End-to-end flow on a Kokkos `.cpp` input (when `--no-probe` is not given): the baseline harness now emits **four** driver sources in one call, one per probe precision. The orchestrator's `spawn_baseline_harness` branch in `_execute_tool` accepts both the legacy single-`driver_source` shape (CUDA / HIP / SYCL / OMP-offload) and the new v1 `drivers` shape (Kokkos), writing each one to `baselines/<stem>/probe/<precision>/driver.cpp`. The **double** driver is additionally copied to `baselines/<stem>/driver.cpp` as the canonical splice scaffold — NOT the quad driver, even though `profile.baseline_precision="quad"`. This is the **role split**: the canonical baseline driver is the splice target the rewriter's Kokkos kernel gets pasted into, so it has to be a real Kokkos `.cpp` source that compiles under `g++ -std=c++20 -O2 -fopenmp` against the bundled `./kokkos/` install; the quad probe driver is plain C++ + quadmath (`sqrtq`, `sinq`, plain host `for` loops, `std::vector<__float128>`) because Kokkos ships no `__float128` math overloads (`Kokkos::sqrt(__float128)` does not exist — verified empirically against the bundled headers), so a quad-as-Kokkos-driver is fundamentally uncompilable and would break the splice chain at `compile_rewritten_driver`. The quad driver's *ground-truth* role is preserved through **oracle promotion**, described below. After the baseline chain runs (compile + run, where `run_baseline_driver` writes a double-precision `baselines/<stem>/reference.json`), the orchestrator issues **8** `probe_step` calls (4 precisions × 2 seeds = `{42, 43}`) followed by **1** `probe_compare` call. The resulting `evidence.json` is loaded by `_format_probe_evidence_for_analyst` and APPENDED to the analyst's task string (not prepended, not passed as a tool arg — the LLM cannot smuggle a verdict in).

**Oracle promotion.** Immediately after `probe_compare` returns `status='ok'`, the orchestrator's `probe_compare` branch in `_execute_tool` copies `baselines/<stem>/probe/<baseline_precision>_seed42/reference.json` over `baselines/<stem>/reference.json` (the file `compare_outputs` reads as the baseline by contract — no comparator change required). For Kokkos this promotes the quad probe reference into the canonical slot, overwriting the stale double-precision reference `run_baseline_driver` wrote earlier in the chain, so the finish-gate comparator measures the rewritten kernel against true ground truth instead of against a same-precision double oracle. The guard is `baseline_precision != "double" AND baseline_precision in probe_precisions` — for profiles where `baseline_precision == "double"` (CUDA / HIP / SYCL / OMP-offload in v1), promotion is a no-op; for profiles whose probe pipeline is disabled (`probe_precisions=()`), the `probe_compare` branch is never reached. Failures (missing `quad_seed42` probe reference, `OSError` on copy) are non-fatal — `compare_result` is returned verbatim and the comparator runs against whatever `reference.json` is in place. The promotion happens at the orchestrator boundary rather than inside `compare_outputs` so the comparator stays fully language-agnostic at the file-path level. `run_baseline_driver` is still called (it smoke-validates the double splice scaffold compiles and runs before the rewriter touches it); the fact that its `reference.json` gets overwritten downstream is intentional, not redundant.

`probe_step(kernel_stem, precision, seed, language_id)` is a fused compile-and-run tool (chosen over split tools to cap HITL approvals at 8 per kernel, not 24). For seed=42 it consumes the template at `baselines/<stem>/probe/<precision>/driver.cpp` as-is; for seed≠42 it copies the template to a sibling per-seed directory at `baselines/<stem>/probe/<precision>_seed<seed>/driver.cpp` and rewrites exactly one line matching the regex `_RNG_SEED_LINE_RE` (exactly-one-match is required — zero or multiple matches is a tool error). Then it shells out via the shared `_compile_driver` / `_run_driver` helpers (so `AGENT_PRECISION_KOKKOS_ROOT` and `AGENT_PRECISION_RUN_TIMEOUT_SEC` apply unchanged) and writes `baselines/<stem>/probe/<precision>_seed<seed>/{driver, reference.json}`. `language_id` is injected by `_execute_tool` (operator never types it; the orchestrator LLM never passes it — it's stripped from the tool's input_schema). Cell failures are non-fatal: a missing or unreadable `reference.json` simply doesn't contribute evidence.

`probe_compare(kernel_stem, language_id)` is pure I/O — it loads every `baselines/<stem>/probe/<precision>_seed<seed>/reference.json`, treats `quad_seed42` as ground truth, and emits `baselines/<stem>/probe/evidence.json` with per-output (output_name, precision, seed) entries. Per-cell status is one of `ok`, `missing` (no reference.json), `load_error` (unparseable JSON), `shape_error` (mismatched keys / lengths vs ground truth), or `no_quad_partner` (this cell exists but the same-seed quad cell does not). Only a missing `quad_seed42` cell hard-errors (`status='error'`); every other cell-level problem is tolerated and reported per-entry, because the analyst can still reason from a partial table. The comparator reuses `_iter_leaf_pairs` and `_shape_error` from `compare_outputs` verbatim — no refactor was needed.

Stale-baselines note: existing `baselines/*/driver.cpp` files written before the four-driver harness schema landed are stale and will mismatch the new probe directory layout. Operator: `rm -rf baselines/<stem>/` to regenerate from scratch on the next run.

Cost: +~3 minutes wall-clock per Kokkos kernel and 9 extra HITL approvals (8 `probe_step` + 1 `probe_compare`). `AGENT_PRECISION_ORCHESTRATOR_TIMEOUT_SEC` (default 600 s) may need to climb to 900 s on slower hosts. The fused-tool design is deliberate — splitting `probe_step` into compile/run would triple the HITL approval count, which is the primary v0 UX cost. (`MAX_TURNS` was originally raised from 40 to 60 to make room for the probe; it was raised again from 60 to 150 in Step 5c for the per-variable analyst pipeline — see "The per-variable analyst pipeline" below.)

**Post-analyst probe-consistency gate — removed in Step 5b.** The historical `_probe_consistency_gate` (and the `check_analyst_verdict_against_probe` invocation in the `spawn_analyst` branch of `_execute_tool`) was superseded by empirical per-variable gating in the new pipeline (`test_variable_downcast` per candidate, plus `test_variable_union_downcast` / `bisect_variable_downcast` on the survivors). The `check_analyst_verdict_against_probe` helper in `workflow/tools.py` is retained for tests and possible future use, but nothing on the production path calls it.

If you change probe behavior, the source of truth is `workflow/tools.py` (the two tools plus `check_analyst_verdict_against_probe`, `_RNG_SEED_LINE_RE`, `_PROBE_SEEDS=(42, 43)`, `QUAD_PROBE_TOKEN = "__float128"`, `QUAD_LIB = "-lquadmath"`); the orchestrator's probe-tool descriptions live in the system prompt in `orchestrator.py`; the probe-evidence injection into the per-variable analyst pipeline lives in `_execute_tool`'s `spawn_candidate_finder` / `spawn_variable_analyst` / `spawn_analyst_finalizer` branches (NOT as LLM-visible arguments); and the per-language gate is `LanguageProfile.probe_precisions` plus `LanguageProfile.baseline_precision`. The per-variable analyst schemas (`CANDIDATE_FINDER_OUTPUT_SCHEMA`, `VARIABLE_ANALYST_OUTPUT_SCHEMA`, `ANALYST_FINALIZER_OUTPUT_SCHEMA`) are unchanged by the probe — their prompts got a "PROBE EVIDENCE" addendum describing how to read the numbers. Extending the probe to CUDA / HIP / SYCL / OMP-offload is the obvious Commit 6 candidate: set those profiles' `probe_precisions` and `baseline_precision`, and update the per-language baseline_harness prompts to emit the four-driver shape; no `_execute_tool` change should be needed because the dual-shape dispatch is already in place.

### Tolerance vocabulary and plumbing

There are three distinct precision concepts kept deliberately separate in this code, prompts, and tests:

- **`sig_figs` (significant figures)** — relative tolerance on the kernel's *output*.
- **`decimal_digits` (decimal places after the point)** — absolute tolerance on the output.
- **Floating-point storage precision** (`float`, `double`, `float-float`, …) — the *mechanism* the analyst chooses per variable. A kernel can hit a 6-sig-fig output target using a mix of internal storage precisions.

The tolerance is a single dict `{kind, value, source}` flowing through the run:

- `kind ∈ {sig_figs, decimal_digits}` once fixed; the advisor's `unknown` is never propagated downstream — it triggers the documented fallback.
- `value` is a small positive integer (`int > 0`; non-positive values are rejected by `workflow/run.py`).
- `source` is always `'user_cli'` today (the `precision_advisor` agent and its `advisor_unknown_defaulted` fallback were removed; the field is kept for provenance so future non-CLI paths — e.g. an eval harness passing an operator-fixed tolerance — remain distinguishable).

Plumbing: `run_orchestrator(kernel_path, kernel_source, tolerance)` (required kwarg, no default) embeds the tolerance verbatim into the first user message via `_format_tolerance_block()`. The orchestrator LLM is then responsible for inlining the tolerance into the `kernel_source` argument of `spawn_analyst` (as a labeled block the analyst echoes into its `precision_budget` output), into the `task_prompt` of `spawn_rewriter`, and as the separate `tolerance_json` argument of `spawn_verifier` (which `_execute_tool` joins into a labeled TOLERANCE (JSON) section of the verifier's task string).

The per-variable pipeline agents (`spawn_candidate_finder`, `spawn_variable_analyst`, `spawn_analyst_finalizer`) read the tolerance the same way — the orchestrator LLM inlines it into their `kernel_source` argument. The finalizer's `precision_budget` echoes it verbatim into its output, exactly as the monolithic analyst used to; the verifier's contract is unchanged.

The analyst is told, in its system prompt, that the tolerance is a hard constraint and that `emulate` is throughput-negative — preferred only when `downcast` would violate tolerance. The rewriter prompt forbids silently substituting one method for another. Both rules are LLM-side, not Python-enforced.

### Per-variable action enums

The analyst's per-variable `action` enum is `{downcast, emulate, keep}`. `downcast` replaces a type with a narrower hardware type (e.g. `double` -> `float`) and uses `target_precision`; `emulate` replaces a type with a software-emulated pair (currently float-float / Dekker, written inline as `struct ff_t {float hi, lo;}` per the rewriter prompt) and uses `emulation_type`; `keep` leaves the variable alone. The analyst's top-level result also includes a required `rework` object (`{suggested, transformation, rationale, affected_variables}`) for kernel-shape changes such as Kahan summation (when none is warranted, the analyst still returns the object with `suggested=false` and empty fields rather than omitting it), and a required `precision_budget` object (`{target_kind, target_value, source, claimed_output_precision, headroom_argument}`) that links the verdict back to the tolerance. The verifier's `expected_action` enum mirrors the analyst's; its `observed_action` enum adds `unclear`. If you rename any of these tokens, update `registry.py`, `orchestrator.py`'s system prompt, and the tests in `tests/test_registry.py` / `tests/test_orchestrator.py` together — they are deliberately coupled.

### The per-variable analyst pipeline

The monolithic `spawn_analyst` was replaced with a six-stage pipeline that gives the analyst an algorithm to follow instead of asking it to reason about a whole kernel at once. The stages, in order, are:

1. **`spawn_candidate_finder`** — one LLM call. Enumerates every floating-point variable in the kernel and marks each with `downcast_candidate: bool` plus a rank and short rationale. Non-candidates (`false`) are excluded from the empirical stages below and pass through to the finalizer as fixed `action='keep'` entries.
2. **`spawn_variable_analyst` (× N)** — one LLM call per candidate from step 1. Reads only the target variable name plus the kernel source; produces `{variable, notes}` where `variable` is a full `ANALYST_OUTPUT_SCHEMA.variables[]` item (so step 5 can splice it in without renaming). Single-shot only; no ensembles.
3. **`test_variable_downcast` (× N)** — deterministic tool. Splices a singleton downcast alias into a per-variable copy of the baseline driver at `baselines/<stem>/varprobe/singleton_<var>/`, compiles, runs, and compares against the quad oracle at the operator's tolerance. Pass / fail is recorded per candidate.
4. **`test_variable_union_downcast`** — deterministic tool. Splices ALL step-3-passing variables together into a single driver, compiles, runs, compares. If the union passes, the survivors are the final downcast set. If it fails (variable interactions), step 5 runs.
5. **`bisect_variable_downcast`** — deterministic tool, invoked only on step-4 failure. Drops candidates in candidate-finder rank order (via the `variable_names[]` list passed in) until a passing subset is found; that subset becomes the final downcast set. Empty-passed-subset returns `status='ok'`.
6. **`spawn_analyst_finalizer`** — one LLM call. The orchestrator has by this point mechanically composed `variables[]` from the step-1 non-candidates (fixed `keep`) plus the step-2/3/4/5 survivors (their `variable` blobs verbatim, demoted to `keep` with a specific reason if step 3 rejected them singleton or bisect dropped them from the union). The finalizer is handed this assembled list as `ASSEMBLED VERDICT (JSON):` and asked to fill in ONLY the wrapper blocks (`precision_budget`, `rework`, `overall_notes`); it MUST echo per-variable `name/action/target_precision/emulation_type` verbatim. Output conforms to `ANALYST_OUTPUT_SCHEMA` verbatim — the verifier reads `analyst_verdict_json` and does not need to know the pipeline replaced a single call.

Design rationale: the pipeline replaces the ensemble-aggregator consistency mechanism (which was `AGENT_PRECISION_ANALYST_K` folding K noisy verdicts through majority vote) with empirical per-variable gating against the compiled driver. False-conservative errors (a candidate incorrectly demoted to `keep`) are recoverable — the finalizer's output goes through the verifier and comparator like any other verdict. False-aggressive errors (a candidate accepted that shouldn't be) are what the union step and the bisect step catch. The `AGENT_PRECISION_ANALYST_K` / `_T` env vars are inert on this path.

**Two-splicer contract for singleton / union / bisect tests.** `test_variable_downcast`, `test_variable_union_downcast`, and `bisect_variable_downcast` all funnel through a single dispatcher in `workflow/tools.py:_splice_singleton_variable(driver_text, profile, variable_name, target_cxx)` that tries two mutation strategies in order. **Strategy 1 (`_splice_singleton_alias`)** rewrites the `using <VariableName>Type = ...;` alias line the baseline_harness emits for every floating-point kernel parameter — this is the happy path for View parameters and scalar parameters, and is the only strategy the union / bisect tests need in the common case. **Strategy 2 (`_splice_singleton_local`)** is a fallback for variables that are NOT kernel parameters (locals like `eps2`, `r2`, `inv_r`, `ax`, `ay`, `az` in nbody-shaped kernels): it rewrites the unique local declaration line matching `[<indent>][const ]<double|float> <name> = <RHS>;` inside the kernel sentinels. The dispatcher falls through to strategy 2 ONLY when strategy 1 returns the specific "alias line absent" error (prefix-matched via `_ALIAS_NOT_FOUND_ERR_PREFIX = "No \`using "`); any other strategy-1 error (duplicate alias, RHS-not-downcastable) stays a hard error rather than silently masking a real harness-contract bug with a body edit. When neither strategy matches, the dispatcher returns a combined error naming both attempts with `Parameter attempt:` / `Local attempt:` labels so an operator can distinguish "not a parameter and not a local" from "not a parameter and its local decl is outside the safe subset". The safe subset for strategy 2 is deliberately narrow: it accepts single-line `double`/`float` decls with an initializer, and rejects `auto`, arrays, multi-variable-per-line decls (both `double a, b;` — caught by the regex — and `double a = 0.0, b = 0.0;` — caught by a post-regex `_has_top_level_comma` scan of the RHS that ignores commas nested inside `()` / `[]` / `{}` so legitimate initializers like `pow(x, 2.0)` still match), no-initializer decls, comments, and `long double`. No-op mutations (the variable is already at `target_precision`) are treated as errors, not silent successes, to prevent a false-positive `VERDICT: pass` on a variable that was never actually downcast. Semantic caveat: mutating `const double inv_r = <RHS>;` to `const float inv_r = <RHS>;` changes only storage precision — the RHS is still evaluated in double and then rounded once at assignment. That is a different signal than a parameter downcast (which affects every operation on the parameter) but still measurable via the tolerance gate, and the finish-gate comparator catches any downstream regression. Source of truth is `workflow/tools.py` (`_splice_singleton_variable`, `_splice_singleton_alias`, `_splice_singleton_local`, `_has_top_level_comma`, `_LOCAL_DECL_RE_TEMPLATE`, `_ALIAS_NOT_FOUND_ERR_PREFIX`); the ~23 tests in `tests/test_tools.py` under the `# ---------- local-declaration splicer (Step 3 fallback) ----------` header pin the contract.

The per-variable pipeline is Kokkos-only in practice: it depends on the baseline harness, the precision-alias contract, and `compare_outputs` against a compiled driver. On non-Kokkos profiles the orchestrator still enumerates the LLM tools, but `test_variable_downcast` / `test_variable_union_downcast` / `bisect_variable_downcast` have no compilable substrate to run against and the pipeline degenerates to `candidate_finder -> variable_analyst (× N) -> analyst_finalizer` reasoning from source. Fixing this is the same work as extending the probe pipeline to those profiles.

If you change the pipeline shape (add/remove/reorder a stage), update `orchestrator.py`'s system prompt (the enforcement paragraph in "Architecture"), `flowchart.md`'s "The per-variable analyst pipeline (step 6)" section, README's Workflow diagram + tools table, and `evals/layer2/score.py`'s `_KNOWN_TOOLS` set in the same change.

## Conventions

- No linter, formatter, or typecheck configured. Don't invent commands; ask before adding tooling.
- Layer 1 tests (workflow plumbing) live in `tests/`; run with `python -m pytest -q` for a terse pass/fail, or `python -m pytest -v` to see each test's docstring appended to its node id as a self-describing checklist (a `pytest_collection_modifyitems` hook in `tests/conftest.py` does the appending). They monkeypatch `anthropic.Anthropic` and make zero network calls.
- Layer 2 (agent-judgment) evaluation harness lives in `evals/layer2/` and grades the workflow end-to-end over the 17-kernel `test-kernels/` corpus. `evals/layer2/run.py` is the batch driver — it spawns `python -m workflow.run --auto ...` per kernel as a subprocess, then reads `baselines/<stem>/orchestrator_trace.jsonl` and scores it. `evals/layer2/expected.py` is the hand-transcribed per-variable ground-truth registry mirroring `test-kernels/SUMMARY.md` (the two are asserted to stay in sync by `tests/test_evals_expected.py`); when a kernel's empirically-correct verdict diverges from SUMMARY (catastrophic-cancellation cases like `vector_add` / `saxpy_bounded` / `saxpy.cu`), the entry is tagged `REVISED: empirical` with an evidence pointer. `evals/layer2/score.py` is a read-only trace parser that re-derives the finish-gate state by walking the trace (mirrors `_FinishGateState` in `orchestrator.py`) and a closed `_KNOWN_TOOLS` set so a new spawn tool can't silently slip past the scorer. `evals/layer2/report.py` aggregates a `run.py --output` JSON into a human-readable text report plus a smaller aggregated JSON; exit `0` = all pass and no regressions vs expected, `1` = any fail or regression, `2` = config error. Per-kernel wall-clock bound: `AGENT_PRECISION_ORCHESTRATOR_TIMEOUT_SEC` (default `600`). Run output (`results.json` + logs) lands in `evals/results/<timestamp>_<label>/` and is `.gitignore`'d; reproduce a baseline by re-running the harness. The trace JSON shape is pinned to `schema_version: 2` in both the `run.py` emitter and `report.py` consumer. The harness does not import from `workflow.*` — it is a strict subprocess-contract consumer, so it cannot accidentally smuggle workflow internals into the grading signal.
- Python 3.10+ (uses `dict | None`).
- Keep agent system prompts in `registry.py`, not scattered. Keep orchestrator prompt in `orchestrator.py`.
- `flowchart.md` is a Mermaid view of the orchestrator loop (tools, HITL pause, rejection feedback). It is documentation only — nothing in `workflow/` reads it — but if you change the pipeline (add/remove a spawn tool, change the HITL contract, change what rejection returns), update `flowchart.md` in the same change so it doesn't drift from `orchestrator.py`. README's "Workflow" section embeds the same diagram (kept in sync manually).

## Planned next steps (not yet implemented)

Documented here so future sessions don't relitigate decisions or accidentally double-implement them. None of these are in the code today.

- **Kernel-extractor agent.** When inputs eventually contain more than one kernel function in a single file (or the kernel is buried in a larger translation unit), a one-shot LLM agent will identify the target kernel function and slice it out into a standalone source before the analyst and baseline-harness run. v0 sidesteps this by assuming one obvious kernel per file and letting the baseline-harness agent infer the function name; `run_orchestrator` already accepts an optional `kernel_name` argument that the extractor could populate. When this lands, the per-stem baseline directory likely becomes `baselines/<file_stem>__<kernel_name>/` so multiple kernels per file don't collide.
- **Probe pipeline for non-Kokkos profiles.** Commit 6 candidate. v0 ships the probe wired up end-to-end for Kokkos only (`probe_precisions = ("quad", "double", "float", "mixed_io")`, `baseline_precision = "quad"`); CUDA / HIP / SYCL / OMP-offload all set `probe_precisions = ()` and the orchestrator silently skips the probe for them. Extending to a new profile is two edits: (1) populate that profile's `probe_precisions` and `baseline_precision` in its `workflow/languages/<id>.py`, and (2) update its baseline_harness system prompt in `registry.py` to emit the v1 multi-driver `drivers` shape (one driver source per precision) rather than the legacy single `driver_source` shape. The orchestrator's `spawn_baseline_harness` branch in `_execute_tool` already dispatches both shapes, so no router change is needed. The hard parts are per-language: CUDA / HIP have no obvious "quad" — you'd likely set `baseline_precision = "double"` and drop quad from the matrix; SYCL / OMP-offload share the `.cpp` suffix with Kokkos so the `__float128` / `-lquadmath` Kokkos hack may or may not transfer cleanly depending on the host compiler. Defer until at least one non-Kokkos kernel has actually been smoke-validated through the dynamic-verification chain so we're not flying blind.
- **Smoke-validation of HIP / SYCL / OMP-offload profiles.** HIP (and the not-yet-landed SYCL / OMP-offload) profiles ship as unit-tested stubs only. End-to-end smoke against a real `hipcc` / `icpx` / `clang++ -fsycl` / `clang++ -fopenmp -fopenmp-targets=...` toolchain is deferred until a host with the respective runtime is available. The CUDA chain was smoke-validated on `vector_add.cu --sig-figs 6 --auto` (a numerical mismatch surfaced at the comparator step and was correctly retried by the analyst, which is the intended failure-recovery path; the underlying `vector_add.cu` precision issue is a fixture concern, not a workflow bug). SYCL's `_detect_from_source` and the tightened Kokkos probe (now requires `<Kokkos_Core.hpp>` OR `Kokkos::` OR `KOKKOS_LAMBDA`) are similarly unit-tested but not exercised against a real source corpus — Phase C-2 added the disambiguation logic, but the only `.cpp` kernels in `test-kernels/` are Kokkos, so the SYCL branch has never been hit from a real input file.
- **JLSE / async toolchain migration.** Current host has Kokkos+CUDA locally; future runs will submit compile/run jobs to a remote scheduler. Designing the verifier tool interfaces around `{status, stdout, stderr, artifacts}` now means the orchestrator loop doesn't change when "run" becomes "submit job, poll, fetch artifacts".
- **Emulation library upgrade.** v0 writes `struct ff_t {float hi, lo;}` plus Dekker two-sum/two-prod inline (per the rewriter prompt) rather than vendoring a real float-float library. Replacing this with a proper header is straightforward once we have mechanical verification to catch regressions.
- **Rejected: multiple per-method analysts.** Considered splitting the analyst into priority-ordered specialists (downcast-first, then emulate, then rework). Rejected: more moving parts, breaks the "one entry in `AGENTS` per agent type" invariant, and gives no clear win over a single analyst with a richer output schema. Revisit only if a single analyst proves to systematically under-explore one method.
- **Rejected: LangGraph (or similar framework).** Considered for state management as the pipeline grows. Rejected for v0: adds a dependency and an abstraction layer for a workflow that is still linear and synchronous. Revisit only if we get *parallel* branches (e.g. multiple rewrite candidates evaluated concurrently), async/durable state across long jobs, or a non-CLI frontend. Intermediate alternatives to try first: an explicit `OrchestratorState` dataclass, or pickled-message resume. The harness -> compile -> run trio specifically is a tempting subgraph candidate (shared `kernel_stem`, shared `baselines/<stem>/` paths, eventually a "which compiler" gate before compile), and was also rejected for v0 for the same reasons plus three more: (a) it would collapse three HITL approval points into one, undermining v0's whole point that every tool call is shown to the user before it runs; (b) the "which compiler" gate is a one-line `shutil.which("g++")` / `shutil.which("nvcc")` check (and a kernel-extension dispatch) *inside* `compile_baseline_driver`, not a graph node — same spirit as the existing env-var validation block; (c) compile and run are deterministic `subprocess.run` calls, not LLM nodes, so a graph framework here is mostly ceremony around two shell-outs. Revisit specifically for the trio if a *second* consumer of harness -> compile -> run appears outside the main orchestrator (e.g. a batch evaluator over `test-kernels/`), if rewrite candidates fan out in parallel and each needs its own compile+run, or if the JLSE migration forces async/durable state across long-running jobs.
